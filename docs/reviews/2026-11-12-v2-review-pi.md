# Adversarial review of the v2 decision record

Date: 2026-11-12. Reviewed `docs/assumptions.md` v2, `docs/research-error-model-and-charsets.md`, and the first adversarial review.

**Verdict:** v2 substantially improves the architecture, but its tables are not yet an executable specification. Several valid inputs can acquire spurious defects, and malformed inputs still have multiple permitted outputs. The most urgent gaps are Flatten semantics, header termination precedence, boundary scope across decoded sources, and codec state transitions. Section L is not yet a sufficient or fully testable M1 exit gate.

I accept the owner's decisions: the three-variant `ParseError`, default failure with opt-in Flatten, diagnostic WHATWG-compatible charset policy, no automatic UTF-8 override of declared single-byte labels, and M1/M2/M3. Recommendations below make those decisions implementable; they do not reopen the strict-Latin-1 debate. Where v2 contradicts itself, the necessary clarification is identified explicitly.

These are specification counterexamples, not results from an eml implementation. In quoted examples, `\r`, `\n`, `\t`, and `\xNN` denote actual bytes. Multiline message examples use LF framing, which v2 supports. No implementation or existing file was changed. The closure matrix at the end accounts for **every previous blocker and major finding**.

## Blockers

### V2-B1 — Flatten cannot currently satisfy the limit or decoder contracts

**Sections:** B.1, B.3–B.6, E.3, F. **Previous findings:** B01, M11.

**Problem:** Flatten is defined for an “over-limit entity,” but several limits are not entity-local. Flattening a subtree fixes depth, but does not automatically fix exhausted part or diagnostic budgets. The public transfer-decoder result is only a byte array plus diagnostics, so it has no way to return `LimitExceeded` under the default policy. A pure deferred decode also cannot silently decrement a budget retained in the original immutable Message.

**Counterexamples:**

- With a configurable part budget of two child entities, encounter a third sibling. Creating an opaque third child already exceeds the cap. Flattening each subsequent sibling permits arbitrarily many nodes. Dropping them violates preservation. Flattening their parent can work, but is a different, currently unspecified operation.
- At exactly 10,000 diagnostics, another malformed byte requires both its own diagnostic and `LimitReached`. Even emitting only the latter exceeds the cap unless a slot or out-of-band status was reserved. With a zero diagnostic budget, reserving one ordinary slot cannot work.
- A QP leaf containing many repetitions of `=zz` is cheap to frame but can exhaust the diagnostic budget only when its decoder runs. F cannot express the default limit error. What bytes does opt-in Flatten return from that decoder: encoded bytes, a decoded prefix, or nothing? Encoded bytes disguised as decoded output would be particularly dangerous.
- Two separately requested leaf decodes can each produce 6,000 diagnostics. Does the shared 10,000 budget apply across those calls, only within `decode_all`, or only to structural parsing? There is no defined state transition or aggregation rule.

**Recommendation:** retain fail-by-default and opt-in Flatten, but specify a limit/action matrix. For a global cap, identify which existing ancestor is collapsed, whether previous descendants/diagnostics are replaced, and how its complete raw span remains accessible. Reserve an unambiguous limit/completeness status that cannot itself be suppressed by the diagnostic cap. Define budget scopes per operation: one ledger for parse including eager embedded decoding, one for each explicit decode operation, and one shared ledger for `decode_all`, unless an explicit threaded context is introduced. Give bounded decode functions an error/outcome channel; do not pretend the tuple in F covers limit failures. Test zero, exactly-at-limit, and one-over-limit cases for every budget and both policies.

### V2-B2 — Header admission and header termination still contradict each other

**Sections:** B.1–B.2, D.2–D.5, E.4. **Previous findings:** M02; parts of B01.

**Problem:** B.1 says a non-field first line is `NoHeaderBlock`; B.2 and D.4 accept a first continuation. D.4's unconditional EOF row contradicts its body-start row. “Invalid characters … space” conflicts with the explicitly allowed space before a colon. These cannot be resolved by implementing the rows independently.

**Counterexamples:**

| Input | Competing outcomes |
|---|---|
| `\tgarbage\n` | No valid `name:` first line, hence `NoHeaderBlock`; or a synthetic field and success even though no real field ever appears. |
| ` \n` | `EmptyInput` because all whitespace; or an accepted initial continuation. |
| `X: y\nbody` | The anomalous final line starts the body; or EOF without an empty line makes the **whole input** headers with an empty body. |
| `X : y\n\nz` | Valid initial field under B.2/D.5; or invalid-space field-name recovery under D.4. |
| `\xEF\xBB\xBF` | BOM skipped, leaving empty logical input; or non-whitespace source that lacks a header block. |
| `\nbody` | Empty header block under D.3; root rejection under B.1. An empty MIME-part header block, in contrast, is explicitly accepted. |

A similar ambiguity applies to BOM followed by `From `: is “line one” physical source line one, or line one after the BOM prefix is skipped?

**Recommendation:** define the ordered root-admission algorithm separately from MIME-part headers. State whether an orphan initial continuation alone satisfies admission, and make the other text agree. Define the exact whitespace byte set for `EmptyInput`, and whether that check occurs before or after recognized prefixes. Make the EOF-only-header outcome conditional on **no earlier transition to body**. Exclude trailing pre-colon SP/TAB from the invalid-field-name row. Specify separate behavior for a root, a MIME body part, and an embedded message. Freeze exact Result, body offset, field list, and diagnostics for the examples above before M1 implementation.

### V2-B3 — Ancestor boundary recognition must stop at a decoded-source boundary

**Sections:** C.2, D.4, E.3–E.4. **Previous findings:** B03, M10.

**Problem:** E.4 says ancestor boundaries apply “inside embedded messages” without distinguishing raw identity-encoded nesting from a new decoded source. An outer raw delimiter must terminate a raw child even during its headers. It must **not** be recognized merely because transfer decoding produces matching bytes in a new source. C.2 gives sources identities but E does not use them to constrain boundary scope.

**Counterexample:**

```text
Content-Type: multipart/mixed; boundary=o

--o
Content-Type: message/rfc822
Content-Transfer-Encoding: quoted-printable

Subject: nested

=2D=2Do
inside
--o--
```

The raw outer message has one child and closes at the final `--o--`. The decoded embedded body begins with literal `--o\ninside`. Reusing the outer active-boundary stack for that source can terminate/restructure the parent at **data that was not a delimiter in the parent's source**. The analogous base64 case has the same problem. Likewise, equal boundary names in different source domains are not necessarily a collision.

D.4 lookahead has the complementary problem: searching for the next empty/header-looking line without stopping at an active raw delimiter can use a later sibling's headers as evidence for classifying the current child's malformed header lines.

**Evidence:** [RFC 2046 §§5.1.1–5.1.2](https://www.rfc-editor.org/rfc/rfc2046.html#section-5.1.1) defines raw multipart encapsulation and outer-boundary recognition. [RFC 6532 §3.5](https://www.rfc-editor.org/rfc/rfc6532.html#section-3.5) permits nested transfer encodings; decoding creates a new parsing domain, not new parent delimiters.

**Recommendation:** scope the boundary stack by source. Bound the raw entity first; then decode and parse its derived source with a fresh enclosing-boundary context. Identity-encoded nested messages sharing a source retain the appropriate enclosing context. Header lookahead must stop at the entity end or earliest applicable raw boundary, not cross into sibling headers or epilogue. Add the QP example, a base64 equivalent, and a same-name-boundary-in-derived-source case to M1.

### V2-B4 — The base64 table mishandles normal padding unless an undocumented state is added

**Sections:** F/base64, E.3, L. **Previous finding:** M06.

**Problem:** after `=` at position two, the table says the quantum ends. The second required `=` in a normal one-byte encoding is then at position zero, where the table says to flag it as invalid. There is no “expecting the second padding byte” state. The generic “any other byte” row also includes `=` unless exclusions/priority are explicit, and the ordinary alphabet row overlaps alphabet-after-padding.

**Counterexamples:**

| Input | What must be specified |
|---|---|
| `QQ==` | Must yield `A` with **no invalid-padding diagnostic**. Literal application of the current rows warns on the second `=`. |
| `QQ=` | Missing second required pad; currently indistinguishable from a complete padded quantum. |
| `QUI=` | Normal two-byte output `AB`; no padding warning. |
| `QUJD` | Full unpadded quartet `ABC`; quartet emission and clean EOF at position zero are not stated. |
| `QQ===` | Third pad is excess; distinguish it from the legitimate second pad. |
| `QQ\r\n==` | Whitespace must preserve the pending-padding state. |
| `QQ==Qg==` | The chosen output `AB` is clear, but the warning set is not: it must not falsely diagnose both legitimate second pads. |
| `Q=Q`, `=QQ==`, `QR==` | Mid-quantum padding, leading padding, and nonzero pad bits need separate state/consumption expectations. |

**Recommendation:** replace the overlapping predicates with a byte-class × decoder-state transition table. Include ordinary quartet completion, pending second pad, after-padding, empty input, and each EOF state. Preserve the decided concatenated-stream recovery if desired, but define when `Base64DataAfterPadding` is counted and which padding errors coexist. Assert **diagnostics as well as decoded bytes** on valid vectors; output-only tests would miss this bug. Do not treat F's prose as a complete codec specification yet.

## Major findings

### V2-M1 — D.4 is a different heuristic from RFC 7103, with an undefined continuation target

**Sections:** D.4, D.6, H.1. **Previous findings:** M02, M03.

**Problem:** preserving an anomalous line as its own span is good. Refusing to include it in a recovered field value is a separate semantic choice, not RFC 7103 §7.2. That RFC's selected recovery is option 3: insert one space and append the line to the previous field. v2 implements only its header/body-boundary heuristic while labeling the whole outcome RFC 7103 recovery.

**Counterexample:**

```text
Subject: alpha
beta
 gamma
X: y

body
```

RFC 7103-style recovery can display `alpha beta gamma`. Under v2, `beta` is an anomalous record. Is ` gamma` appended to Subject, the anomaly, or a synthetic field? The document does not say. This also affects structural fields:

```text
Content-Type: multipart/mixed;
boundary=b
X: y

--b

payload
--b--
```

A continuation-repairing parser sees a multipart; v2 may see an unusable Content-Type or a multipart without a boundary, depending on its separate parameter parser. Merely retaining `boundary=b` raw does not make these interpretations agree.

**Evidence:** [RFC 7103 §7.2](https://www.rfc-editor.org/rfc/rfc7103.html#section-7.2) explicitly selects its option 3 under the lookahead conditions.

**Recommendation:** either implement a recovered field view that references separate anomalous source spans, or name/document this as an intentional deviation. Define which record a following WSP continuation belongs to. Do not let synthetic nameless fields be mistaken for ordinary field occurrences. Add field-view and structure assertions for both examples. Interoperability disagreement is acceptable when diagnosed; attributing the different result to RFC 7103 is not.

### V2-M2 — E.3 mixes terminal decisions, actions, and postconditions in one ordered table

**Sections:** E.1–E.3. **Previous finding:** B03.

**Problem:** “steps … in order” does not say whether rows are first-match terminal rules or a sequence of transformations. Either straightforward reading fails:

- A recognized base64 multipart with a usable boundary but **no delimiter** matches “ignore CTE, split as multipart” before “start delimiter never appears.” Is the result Multipart or Opaque?
- A malformed encoded embedded message matches “decode, then Embedded” before the row handling a recursive parse failure. That later row is a postcondition, not an independent input predicate.
- `LimitExceeded` from the recursive parse has no row. B.3 presumably controls it, but E must not swallow it as `NotAMessage` or bypass Flatten.

**Counterexamples:**

- `Content-Type: multipart/mixed; boundary=b\nContent-Transfer-Encoding: base64\n\nQUJD`.
- `Content-Type: message/rfc822\nContent-Transfer-Encoding: base64\n\nQQ==` decodes to `A`, which fails embedded admission.
- `Content-Type: message/rfc822\n\n` has an empty embedded source.

**Recommendation:** separate preliminary CTE/type interpretation, terminal opaque decisions, multipart scanning, and embedded decoding/parse-result handling. Spell out all three recursive error variants and both limit policies. For the first example, specify `Opaque(StartDelimiterNotFound)` plus `EncodedMultipart` if that is intended—not an accidentally successful empty Multipart. State diagnostic accumulation order when several conditions hold.

### V2-M3 — Boundary matching still lacks suffix classification and multipart lifecycle states

**Sections:** E.3–E.4, B.4, K.3. **Previous finding:** B03.

**Problem:** exact-match priority is an improvement, but “other text” gives a diagnostic without saying whether the candidate opens or closes. The splitter also lacks explicit BeforeFirst/InsidePart/AfterClose states. Recognition alone cannot tell whether a line creates a child, closes one, or belongs to epilogue.

**Counterexamples:**

1. For boundary `b`, `--b--junk` may be a closing delimiter with junk, or an opening delimiter with trailing text. `--b \t--` poses a related question: is whitespace allowed before the closing marker? Different choices change whether following data is a part or epilogue.
2. A body consisting solely of `--b--\n`: is this a close-without-open malformed multipart with zero parts, or `Opaque(StartDelimiterNotFound)` because no opening delimiter appeared?
3. `--b\n\n--b--\n--b\nX: y\n\nlate`: after the exact close, the later `--b` must not reopen that same multipart; it is epilogue. An ancestor can still terminate a nested epilogue.
4. Outer boundary `a`, inner boundary `a--`, candidate `--a--`: this is simultaneously an **exact outer close** and an **exact inner open**. Exact-before-trailing priority does not help. Innermost-first deterministically chooses the inner open, potentially consuming subsequent outer content into it. With identical boundaries, the first close similarly closes only the inner level. These are diagnosed recoveries, not uniquely meaningful trees.
5. In an ordinary multipart with a leaf child, the containing boundary is an ancestor of the leaf. The wording “current part … each … records MissingCloseDelimiter” would diagnose a normal leaf termination even though a leaf has no own closing delimiter.

**Recommendation:** specify multipart states and a single owner-selection function returning owner, open/close action, exactness, and recovery flags. Explicitly classify close-prefix-with-junk and whitespace-before-`--`. Freeze the chosen collision behavior with examples; expose structural ambiguity/completeness to callers rather than merely calling the recovered tree normal. Emit `MissingCloseDelimiter` only for multipart contexts that actually required a missing close, not every terminated leaf or embedded wrapper. Ensure an unchosen matching ancestor cannot process the same delimiter again.

### V2-M4 — MIME lexical interpretation remains underdefined where it affects the tree

**Sections:** E.1–E.2, E.3 boundary usability, H.4–H.5. **Previous findings:** B02, M03, M04.

**Problem and counterexamples:**

- `Content-Type: multipart/mixed; boundary=b; boundary=c` has two structural values. D.7 handles duplicate **fields**, not duplicate parameters. H.4 preserves alternatives but selects only a filename. E cannot choose its boundary deterministically.
- `Content-Transfer-Encoding: base64 (comment)` is not handled by simply trimming and comparing the entire field string. MIME structured-header lexical processing must be defined before the table. “And similar spellings” is an unbounded, implementation-specific alias set; replace it with an exact list. State the behavior for an empty CTE, multiple tokens, and quoted `"base64"`.
- `boundary="b(comment)"` contains literal parentheses inside a quoted boundary. Those characters are allowed in a boundary. H.5's “trailing comment … never part” must not strip them after unquoting. In contrast, `boundary=b (note; still a comment)` contains a real comment; a semicolon inside it must not terminate the parameter.
- A boundary of 71–200 bytes, `boundary="b "`, or a boundary containing NUL is not covered by the three listed unusable cases. Are they accepted verbatim, trimmed, rejected, or diagnosed? The current table silently treats many invalid values as usable. Length is not the whole boundary grammar.

**Evidence:** [RFC 2045 §5.1](https://www.rfc-editor.org/rfc/rfc2045.html#section-5.1) distinguishes tokens, quoted strings, comments, and case-sensitive boundary values. [RFC 2046 §5.1.1](https://www.rfc-editor.org/rfc/rfc2046.html#section-5.1.1) specifies 1–70 boundary characters, the allowed character set, and no trailing whitespace.

**Recommendation:** promote the required parameter/CFWS scanning into M1, even though filename interpretation waits until M2. Define the exact structural-parameter duplicate policy, including continued/starred boundary parameters if supported. Preserve quote/comment provenance during lexing. If 200 bytes is an intentional compatibility cap, distinguish valid 1–70, tolerated 71–200 with a diagnostic, and unusable values; reject or explicitly diagnose other invalid boundary bytes. Never silently normalize a boundary used for byte matching.

### V2-M5 — The QP table has no ordinary-literal row and ambiguous whitespace consumption

**Sections:** F/quoted-printable, B.4, L. **Previous finding:** M06.

**Problem:** the most common QP input, plain printable ASCII, matches no row. SP/TAB not before a line ending also lacks an explicit ordinary outcome; TAB additionally overlaps “control bytes.” CR/LF overlap the hard-line-ending/control rows. Nonstandard soft breaks are accepted without a stated diagnostic despite B.4's every-recovery rule.

**Counterexamples:**

| Input | Required clarification |
|---|---|
| `hello` | Literal-copy path is absent. |
| `a b` / `a\tb` | Preserve interior literal whitespace, without treating a legal TAB as an arbitrary invalid control. |
| `a  \r\n` | Remove the **whole trailing SP/TAB run**, not only the final byte. |
| `a \t` at EOF | Does the final unterminated encoded line also lose trailing whitespace? The present rule only mentions a following line ending. |
| `a =\r\nb` | The space precedes a soft-break marker, not the end of the encoded line; it is significant. Expected output should be `a b`. |
| `a= \t\r\nb` | Define whether this recovers to `ab`, and which diagnostic records padded soft-break recovery. |
| `=`, `= \t`, `=A`, `=G1` | Specify exactly what is consumed, copied, dropped, and diagnosed for each terminal/incomplete escape. |
| `=\r\nX` / `=\rX` | CRLF must be consumed as one newline, not CR soft break plus literal LF. The lone-CR recovery needs an explicit classification. |

Dropping terminal `=` as Info is an intentional data-discarding recovery, not just a spelling correction; it conflicts with B.4's definition of DataLoss unless that definition is narrowed.

**Evidence:** [RFC 2045 §6.7 rules 3–5 and malformed-input notes](https://www.rfc-editor.org/rfc/rfc2045.html#section-6.7). In particular, SP/TAB immediately before the soft-break `=` need not be removed.

**Recommendation:** define maximal SP/TAB runs, longest newline matching, EOF treatment, and a fallback literal-octet transition. Track pending literal whitespace without rescanning/copying a growing prefix. Document nonstandard soft-break diagnostics and terminal-`=` severity; do not silently equate dropping malformed encoded content with faithful decoding. Add exact-byte **and diagnostic** vectors for the table above.

### V2-M6 — Validation still cannot establish a complete or unambiguous interpretation

**Sections:** B.4–B.6, D.7, E.3, F, G. **Previous findings:** B02, M11, M13.

**Problem:** `validate(message, severity)` only has the original Message, while lazy decoders return diagnostics separately. `decode_all` “produces the complete report” but its result type, relation to Message, deduplication, and budget are unspecified. The severity ordering is also being used as a proxy for completeness, which its assignments contradict.

**Counterexamples:**

- `Content-Transfer-Encoding: base64\n\nQ`: structural parse succeeds; the leaf decode discovers `InvalidBase64Length`/DataLoss. A structural-only `validate(message, DataLoss)` can pass without examining it.
- `Content-Transfer-Encoding: x-uuencode\n\nopaque`: E.3 says Warning, although B.4 defines DataLoss to include bytes that “could not be interpreted.” Flattened unexamined data is DataLoss instead. A DataLoss-only gate cannot consistently distinguish complete from incomplete interpretation.
- Terminal QP `=` is dropped with Info. Meanwhile valid encoded message/global produces `EncodedMessage` Info. Rejecting every Info both rejects valid content and still does not describe what data was lost versus normally decoded.
- Default/explicit 7bit with high bytes is preserved without a diagnostic in E/F. Preserving those bytes is correct; treating severity-only validation as RFC conformance is not.

**Recommendation:** define whether validation covers structure only or forces all supported decoding. Prefer a bounded complete-report operation whose output is the explicit input to policy validation; retain a clearly named structural-only check if useful. Define reporting for opaque/unsupported entities and which contexts `decode_all` visits. Separate completeness/ambiguity/recovery status from a severity threshold, or at minimum give a consistent severity matrix and an explicit “not fully interpreted” predicate. Do not label a severity filter general strict/RFC validation unless it actually performs the required checks.

### V2-M7 — First-wins structure needs a persistent effective interpretation

**Sections:** C.4, D.7, E.1–E.3, F, I.3. **Previous findings:** B02, B03, M11.

**Problem:** D.7 explicitly chooses first-wins for structure but exposes all field values. It does not state how decoding and helpers use that choice. E.3 ignores the declared CTE on multipart; the raw declared field still exists. A later generic decoder can accidentally apply it again. “Because the parser must pick one” is also too strong: opacity is an available alternative, even if first-wins is the chosen recovery.

**Counterexample:**

```text
Content-Type: multipart/mixed; boundary=b
Content-Transfer-Encoding: base64

--b

QQ==
--b--
```

E.3 splits the **raw** multipart. Its child has identity/default CTE, so its body is the literal bytes `QQ==`, not `A`. A generic `decode_all` that applies the parent's declared base64 first or propagates that CTE to children produces a different result. Duplicate CTEs (`8bit` then `base64`) present the same problem if later accessors make a new choice.

**Recommendation:** retain an effective structural type, effective transfer operation, selected occurrence/parameter provenance, and recovery/ambiguity status for each entity. All decoding and helper APIs must use that recorded interpretation, or require an explicitly separate alternative interpretation. Do not recalculate precedence independently in each helper. Add the example and reversed-order duplicate-field cases to M1 tests.

### V2-M8 — The decided charset policy has mutually applicable branches

**Sections:** E.2, G.1–G.4, H.3. **Previous finding:** M01, with implications for M05.

**Problem:** accepting the owner's WHATWG policy does not resolve the ordering between G's exceptions. The current prose can still produce different Unicode output.

**Counterexamples:**

- `charset=us-ascii`, bytes `C3 A9`: G.1's alias rule yields `Ã©`; its next bullet yields `é` using valid-UTF-8 recovery; G.2 says a declared single-byte label is never overridden. If ASCII is an intentional exception, explicitly exclude it from the general prohibition. This needs an owner clarification if it was not intended as an exception.
- `charset=ascii` or `ANSI_X3.4-1968`, same bytes: do ASCII aliases get the special recovery, or does normalization erase their original ASCII identity and turn them into ordinary windows-1252? Normalize policy provenance as well as the decoder label.
- Absent charset with bytes `C3 A9`: does E.2's synthesized ASCII default mean NonAsciiInAscii, or does G.1's absent-label branch apply? `UnknownCharset(label)` cannot describe an absent label without inventing one.
- `charset=utf-8`, byte `FF`: no fallback/error/replacement outcome is stated. A WHATWG decoder can report an error handled in fatal or replacement mode; “WHATWG decoder” alone does not choose that mode. The choice also decides whether H.3's split-word retry ever runs.
- A caller decoder for `iso-2022-kr`: G.3 says known unsupported charsets consult it first; G.4 says replacement labels are left undecoded and never a successful decode. Does the replacement rule override the trusted callback?

**Evidence:** [WHATWG names/labels](https://encoding.spec.whatwg.org/#names-and-labels) and [decoder processing/error mode](https://encoding.spec.whatwg.org/#concept-encoding-process) distinguish label resolution from error handling. The survey itself documents a compatibility choice, not a proof of safe inference for arbitrary hostile bytes.

**Recommendation:** specify an ordered dispatch table over label presence, original normalized label family, WHATWG canonical encoding, support status, callback result, and malformed-byte status. Preserve the decided Latin-1/windows-1252 behavior and no automatic override for declared single-byte labels; clarify the ASCII exception rather than accidentally implementing one. Make chosen encoding, declared label, guessed/lossy status, and diagnostics observable. Define unsupported/replacement/callback precedence and malformed UTF-8 behavior before M2.

### V2-M9 — RFC 2231 conflict handling is still mostly nominal, and “every alternative” can explode

**Sections:** H.4–H.5, B.3, I.1. **Previous finding:** M04.

**Problem:** bounds and sparse sections are good, but recording a gap or duplicate is not a selection algorithm. The text does not decide whether to concatenate across a gap, use only a contiguous prefix, refuse the extended value, or fall back to the plain name. Nor does it order unnumbered extended values versus numbered continuations. Malformed percent escapes and missing charset/language delimiters still have no outcome.

**Counterexamples:**

- `filename=safe.txt; filename*0*=utf-8''evil; filename*2*=.exe`.
- `filename*=utf-8''one; filename*0*=utf-8''two`.
- `filename*0*=utf-8''a; filename*0*=utf-8''b; filename*1*=.txt; filename*1*=.exe`.
- With two alternatives at each of n section indices, eagerly producing “every alternative” full filename constructs **2ⁿ combinations**. Merely bounding index length and section count does not make that acceptable.
- `filename*=utf-8''%GG` and `filename*=utf-8''%00` need distinct malformed-escape and successfully-decoded-control outcomes.

**Recommendation:** preserve raw candidate occurrences without enumerating their Cartesian product. Define a small deterministic resolution result: resolved, ambiguous, malformed, or unsupported, with explicit fallback precedence. Specify whether a gapped or duplicate continuation is ever considered “unambiguous.” Reuse these policies deliberately for structural parameters where applicable; do not let the filename-specific preference silently become a general MIME rule. This remains an M2 specification task, but structural parameter conflicts in V2-M4 are M1 work.

### V2-M10 — “Concatenating all spans” is impossible for the proposed span model

**Sections:** C.1–C.2, K.3, L. **Previous findings:** B04, M13.

**Problem:** entity spans, field spans, field-name/value subspans, body spans, and child spans overlap by design. Concatenating **all** of them duplicates bytes. Derived-source spans cannot be concatenated with original-source spans at all. Conversely, a single whole-source span trivially covers the input even if the parser's detailed spans omit or misclassify every delimiter.

**Counterexamples:**

- `X: y\n\nz`: the entity covers the message, while the field and its name/value cover bytes inside it. A universal span-concatenation test necessarily double-counts.
- An encoded embedded message contributes both encoded bytes in source 0 and decoded bytes in source 1. Only the former belong in a reconstruction of the input.
- In `--b\n\n--b--`, an empty child's region and the closing delimiter's preceding newline need a defined ownership convention. Removing the delimiter newline can leave a zero-length child-header region. Applying root admission or `NoBlankLineAfterHeaders` mechanically can reject/diagnose a legal empty body part.

**Evidence:** [RFC 2046 §5.1.1](https://www.rfc-editor.org/rfc/rfc2046.html#section-5.1.1) defines `body-part := MIME-part-headers [CRLF *OCTET]`; MIME body-part framing is not identical to root-message admission.

**Recommendation:** distinguish reference spans from a designated ordered, non-overlapping **physical coverage partition per source**. Define half-open endpoints, zero-length regions, prefix bytes, anomalous lines, delimiter/newline ownership, and EOF. Test reference-span bounds/containment separately from partition reconstruction. Reconstruct only source 0 for the input identity property; validate derived sources against independently checked transfer-decoding results. Add empty-header/empty-body and EOF-delimiter fixtures before relying on this invariant.

### V2-M11 — Section L is necessary but not a sufficient M1 release gate

**Sections:** A.4, J.1–J.2, K.2–K.5, L. **Previous findings:** B01, M10, M13.

**Problem:** “implemented and tested case by case” cannot prove tables whose rows overlap are correctly composed. “Known-answer vectors” has no required malformed-state coverage. The gate omits Flatten, diagnostic-cap behavior, embedded-source interactions, cross-target output equivalence, and even J's performance tests. Tests can pass by preserving bytes while returning the wrong structure or warning on valid inputs.

**Concrete evidence:** `QQ==` can decode to the right byte but falsely warn; a close-only multipart can satisfy “missing boundaries do not crash” with several incompatible trees; returning all malformed multipart input as opaque can pass many survival-oriented golden tests. The literal span criterion is not satisfiable as written (V2-M10).

**Recommendation:** retain the six existing goals, but require the following observable assertions before declaring M1 complete:

| Gate | Minimum testable obligation |
|---|---|
| Admission/framing | Expected Result, fields, raw spans, separator/body offsets, and diagnostics for V2-B2; root/part/embedded contexts; CRLF/LF/CR and mixed framing. |
| MIME composition | Cross-product cases for unknown CTE, invalid/absent type, usable/missing/colliding boundary, encoded container, and recursive failure—not just one test per row. |
| Boundary lifecycle | Before-first, opening, closing, close-without-open, EOF, preamble/epilogue, empty child, ancestor termination inside headers, and both directions of prefix collision. |
| Source scoping | Encoded embedded messages cannot create parent delimiters; original encoded data and derived-source spans remain accessible. |
| Codec outcomes | Exact bytes **and exact diagnostic kinds/severities/counting policy** for valid, malformed, and truncated base64/QP, including padding and whitespace cases above. |
| Limits | Zero/at/over each limit; independent and combined exhaustion; both policies; no unbounded opaque siblings; cap exhaustion always observable; eager and lazy decode errors. |
| Preservation | Non-overlapping physical partitions plus reference-span invariants; all identity bytes 0–255 survive, not merely one UTF-8 sample. |
| Semantics | Expected tree/child count/body ranges, not merely successful parsing or no crash. Test no spurious empty part after a closing delimiter. |
| Portability | Same golden bytes, structure, and normalized diagnostics on both targets; deterministic ordering. Passing separate broad property tests is not enough. |
| Complexity | Run the doubling families from J on both targets under a documented size/time envelope, with memory/stack ceilings where tooling permits. Pin acceptable ratios/tolerances and record baseline sizes rather than asserting an absolute “never quadratic.” |

Define what is actually being ported from gen_smtp/mime4j: files, selected structural assertions, and intentional deviations. M2/M3-only assertions may be explicitly deferred; they should not be silently removed until a fixture “passes.” Subject/filename/charset production regressions can remain out of M1 under the decided milestone split, but their deferral should be named rather than claiming all production failures are covered.

### V2-M12 — The stated safe-filename policy still permits unsafe basenames

**Sections:** I.1. **Previous finding:** M08.

**Problem:** excluding separators, drive prefixes, controls, bidi characters, reserved device names, and empty names does not exclude `.` or `..`. It also does not exclude an NTFS alternate-data-stream suffix or define trailing-dot/space normalization and collisions.

**Counterexamples:** `..`, `.`, `report.txt:payload`, and two names `report` / `report.` can satisfy significant portions of the written policy while escaping the intended terminal component or colliding on a target filesystem. Sanitization can itself produce one of these names.

**Recommendation:** explicitly exclude dot/dot-dot, colon/ADS syntax and platform-invalid characters; define trailing-dot/space handling, reserved-name checks after normalization, maximum length, and fallback names. Run safety checks after all decoding/transformation. Keep the result only a suggestion, with no uniqueness or safe-file-creation guarantee. State that actual storage should use caller-generated identifiers and safe creation APIs. This is M2 work, not a reason to expand M1 into filesystem handling.

## Minor findings

### V2-m1 — The limits need scope definitions and complexity tests, not just default numbers

**Sections:** B.3, H.4, J.1–J.2. **Previous findings:** B01, M10.

**Problem:** “all limits share one cumulative budget” conflicts with “header bytes/fields per entity,” and depth is a maximum along a path rather than a counter accumulated across siblings. There is no default comment-nesting bound or defined limits for decoded-source retention, parameter count, encoded-word runs, or diagnostic detail. No input cap is a valid owner choice, but does not establish a bounded-memory claim for derived representations.

**Counterexample/evidence:** two entities with 600 KiB of headers are each below the stated per-entity cap but together above a cumulative 1 MiB cap. Repeated QP-encoded embedded wrappers can retain multiple near-input-sized decoded sources. A run of n trailing spaces or n malformed header lines must not trigger n suffix scans. “Find the first empty line, then classify” does not by itself answer each later-header query without additional bookkeeping.

**Recommendation:** give each limit a unit, scope, accounting point, default, and boundary convention, and state how multipart and Embedded edges affect depth. Preserve no default input limit, but document retained-memory scaling and offer/define any decoded-output/retention budget needed by callers. Use precomputed suffix facts or a true bounded state machine for D.4, and pending whitespace runs for QP. Include metadata-heavy, not just body-heavy, doubling tests. Distinguish work in raw bytes, aggregate decoded bytes, and emitted diagnostics.

### V2-m2 — Byte alignment and invalid options still have no contract

**Sections:** B.1, B.3, K.5. **Previous finding:** B01.

**Problem:** `BitArray` is not necessarily byte-aligned. A trailing partial byte has no defined result under the three chosen ParseError variants. Negative/zero limits and contradictory options similarly need defined treatment rather than an assertion/panic in supposedly total parsing.

**Evidence:** [gleam_stdlib bit_array](https://hexdocs.pm/gleam_stdlib/gleam/bit_array.html) distinguishes bit size from byte size. The first review already identified this input-domain gap. Byte-aligned qcheck generators will not expose an accidental unmatched trailing-bit pattern on Erlang.

**Recommendation:** keep the decided error variants, but explicitly define the supported octet-input contract and how it is enforced. Decide whether non-octet input maps to one of the existing errors or is excluded through a separately validated input wrapper; do not silently pad or drop bits. Validate Options at construction, so parsing never sees impossible configuration. Add targeted Erlang tests even if cross-target fuzz inputs remain byte-aligned.

### V2-m3 — Some M2 adoption statements are still promises, not decisions

**Sections:** G.6, H.3–H.4, I.2–I.3. **Previous findings:** M05, M07, M08, M09.

**Problem/counterexamples:**

- NUL preservation resolves M07's main issue, but “many” has no threshold. Identical data can acquire different severities in independent implementations.
- A split encoded-word retry needs a bounded same-charset window, error mode, and whitespace policy. Otherwise repeatedly trying longer adjacent runs can be quadratic, or replacement decoding can prevent the retry from ever triggering. `=?utf-8?B?ww==?= =?utf-8?B?qQ==?=` is a small test: the words individually contain invalid UTF-8 bytes C3 and A9; together they encode `é`.
- “Adapted from RFC 8621” does not identify which rules are changed. Duplicate CID targets across alternatives, missing related `start`, and disposition on a multipart container remain underspecified. Returning a part reference is not enough if two are plausible.

**Recommendation:** mark these as concrete M2 exit tasks, with a stable policy and fixtures before exposing helpers. For CID/Content-Location, retain Missing/Ambiguous outcomes and scope resolution to the selected MIME context. No need to implement them in M1; no basis yet to mark all their first-review findings fully closed.

### V2-m4 — The survey is not evidence that these exact acceptance rules match other libraries

**Sections:** B.1–B.2; survey §§1–2.

**Problem:** the survey's Stalwart row says rejection occurs with “no header field **and no blank line**”; v2 requires a first valid field, except for a continuation exception. Those are not equivalent. Its “every maintained parser … record[s] what they recovered” summary also contradicts its own “None” reporting rows. “Windows-1252 is lossless for real Latin-1” is not a guarantee over hostile bytes containing C1 controls.

**Counterexample:** `\nbody` separates a no-fields-with-blank-line acceptance rule from v2's first-field admission rule. `Subject: x\nbody` is another useful no-separator differential probe. These should be measured, not justified by a general likeness to MimeKit/Stalwart.

**Recommendation:** describe eml's rules as its own policy. Preserve the owner's compatibility choice, but remove reliance on “matches” or “safe/lossless” as a substitute for an exact outcome. Pin comparison versions/options and record actual results for a small admission/recovery matrix before claiming agreement. This is evidence hygiene, not a request to adopt another parser's acceptance set.

## Recommended pre-M1 decision order

1. Resolve V2-B1/B2: operation results, Flatten escalation, and root/part admission states.
2. Resolve V2-B3 and V2-M2/M3/M4: source-scoped MIME state machine and effective interpretation.
3. Complete the codec transition tables, including successful-input diagnostics and limit outcomes.
4. Replace L's span assertion with a per-source ownership invariant; add the explicit gates in V2-M11.
5. Keep charset, filename, address, and helper refinements staged for M2/M3, except MIME lexical rules needed to build the M1 tree.

**Bottom line:** the owner's major product choices are workable. What remains is not another philosophical leniency decision; it is choosing one deterministic, bounded, observable result for each table intersection and EOF state.
